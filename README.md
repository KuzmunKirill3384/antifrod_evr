# План снижения фрода и скамерства в Telegram chat-боте

Документ суммирует **сквозной risk scoring pipeline**, **подробный каталог методов опознавания ботов и автоматизации**, метрики, формулы и ограничения **Telegram Bot API** (сообщения, медиа, callback’и, свои логи; **нет** полного доступа к «железу» и глобальному соцграфу Telegram).

---

## 1. Целевая архитектура

```
Signals → Features → Risk Score → Action Layer
```

| Этап | Содержание |
|------|------------|
| **Signals** | Сырьё: текст, стикеры, voice/video note, время, user id, deep-link payload, нажатия кнопок |
| **Features** | Числовые/категориальные признаки |
| **Risk Score** | $S \in [0,100]$ или вероятность скама $p \in [0,1]$ |
| **Action Layer** | Мягкие/жёсткие действия по порогам |

**Принцип:** избегать бинарного «прошёл/не прошёл» без накопления сигналов; комбинировать видео, поведение, текст, граф (если есть), устройство и репутацию.

---

## 2. Таксономия: что именно вы опознаёте

| Класс | Суть | Типичные сигналы |
|---------|------|------------------|
| **Автоответчик на Bot API** | Скрипт дергает `sendMessage` / нажимает inline с заданным интервалом | Ритм $\Delta t$, детерминизм последовательностей, отсутствие «ошибочных» правок |
| **Human-in-the-loop ферма** | Живой человек, но по скрипту / за деньги | Видео+liveness лучше текста; поведенческие паттерны «конвейера» |
| **Массовый скам-шаблон** | Один текст на тысячи аккаунтов | Дубликаты, низкая энтропия, одни и те же URL |
| **Sybil / мультиаккаунты** | Много личностей с одного контура | IP/ASN/device кластеры, синхронные burst’ы |
| **Угнанный / купленный аккаунт** | Живой профиль, чужое поведение | Смена гео/UA, скачок активности, расхождение лиц при верификации |
| **LLM-спам** | Текст «правдоподобный», но однотипный | Перплексия vs шаблон, повторяемость эмбеддингов, отсутствие длинной персональной истории |

Разные классы требуют **разных порогов** и **разных весов** в общем скоре; один сигнал редко достаточен.

## 3. Детальный каталог методов опознавания ботов

### 3.1 Временные ряды и «биометрия ритма»

**Идея:** у человека распределение интервалов между действиями ($\Delta t$) обычно **не** похоже на идеальный Poisson с фиксированным `sleep()` и **не** на абсолютно равные интервалы.

**Сырые величины (на пользователя / сессию):**

- $\Delta t_i = t_{i+1} - t_i$ — время между **его** сообщениями или между **его** апдейтами (callback, voice и т.д.).
- Окно скольжения $T_{\mathrm{win}}$ (например 15 мин / 24 ч).

**Базовые метрики (уже в pipeline):**

$$
\lambda = \frac{N_{\mathrm{msg}}}{T_{\mathrm{win}}}, \qquad
\mathrm{CV} = \frac{\mathrm{std}(\Delta t)}{\mathrm{mean}(\Delta t) + \varepsilon}
$$

**Дополнительно:**

1. **Коэффициент вариации по логарифму** — убирает влияние редких очень длинных пауз:
   $\mathrm{CV}_{\log} = \mathrm{std}(\log(\Delta t + 1)) / (\mathrm{mean}(\log(\Delta t + 1)) + \varepsilon)$.

2. **Burstiness** (упрощённо): отношение максимального $\Delta t$ к медиане в окне; скрипты с «пачками» и паузами дают характерные хвосты.

3. **Лаг ответа на системное сообщение бота** — время от `message` бота до первого ответа пользователя. Боты часто отвечают **слишком быстро** (меньше человеческого RT нижнего квантиля) или с **подозрительно стабильным** RT по многим диалогам.

4. **Периодограмма / автокорреляция** $\Delta t$: периодические колебания (cron каждые N сек) дают пики.

5. **Суточные паттерны** — доля активности 02:00–06:00 локали пользователя (если известна из `language_code`/ручного выбора/гео продукта); **круглосуточная** ровная активность без «сна» — мягкий флаг (не доказательство: сменщики, фермы).

**Как внедрять:** стрим событий в **OLAP** или time-series store; онлайн — скользящее окно в Redis per `user_id`.

### 3.2 Последовательности действий (не только текст)

Кодируйте каждое событие типом: `TEXT`, `PHOTO`, `VOICE`, `VIDEO_NOTE`, `CALLBACK:pay`, `START:payload`.

**Модели:**

- **$n$-граммы на алфавите действий** — «`START → TEXT → CALLBACK`» встречается у фермы иначе, чем у обычных.
- **Переходная матрица** $P(s_{t+1}\mid s_t)$; расстояние KL до «нормальной» матрицы эталонных пользователей.
- **Скрытые марковские модели / LSTM / Transformer** по последовательности (нужен объём данных).

**Эвристики без ML:**

- Доля шагов, где пользователь **никогда** не отклоняется от «счастливого пути» воронки (0 ошибок, 0 лишних сообщений) при сложном сценарии — подозрительно.
- Число **отмен** («назад», смена выбора) = 0 при длинном флоу — флаг.

### 3.3 Лингвистика и статистика текста

**Цель:** отделить шаблон, спам и LLM-копипасту от живой речи.

| Метод | Описание | Реализация |
|--------|-----------|------------|
| **Энтропия** $H$ | Низкая на символах/словах → шаблон | Гистограмма частот, $H = -\sum p\log p$ |
| **Сжимаемость** | Повторяемый текст сильнее сжимается gzip | `len(compress(s))/len(s)` бенч по корпусу |
| **Jaccard / shingle** | Похожесть близких сообщений | $k$-шинглы, minHash для масштаба |
| **TF-IDF / BM25** | Близость к известным спам-шаблонам | Индекс «плохих» фраз |
| **Эмбеддинги предложений** | Косинус между подряд сообщениями | e5, multilingual-mini-LM; кластеризация |
| **Перплексия языковой модели** (если есть ресурс) | LLM-текст иногда имеет иные статистики | Осторожно: калибровка по языку |
| **Язык** | `language_code` vs детектированный язык текста | Mismatch — флаг |
| **Смесь алфавитов / zero-width** | Обход модерации | Unicode-нормализация NFKC, детект ZWSP |
| **Homoglyph** | `t.me` с кириллическими «е» | Таблицы confusable |

**Ссылочные эвристики:**

- Появление URL в **первых $k$** репликах.
- Количество уникальных доменов / доля `t.me` / известные shortener’ы.
- **Скорость рассылки одной и той же ссылки** разным пользователям (продуктовый слой).

---

### 3.4 Дубликаты, координация и «одна кампания»

**Perceptual / semantic дубликаты:**

- Одинаковый текст (нормализованный) от **многих** `user_id` за короткое время → координированное действие.
- **MinHash LSH** по шинглам для миллионов сообщений.

**Граф сообщений:**

- Рёбро «пользователи с текстовой sim > 0.95 за интервал $\tau$»; искать **клики** и **плотные подграфы**.

---

### 3.5 Граф социального / продуктового взаимодействия

В рамках **вашего** бота и смежных чатов:

- **Исходящая степень:** скольким уникальным peer’ам пользователь «разослал» рефералку / инвайт.
- **Reciprocity:** доля контактов, ответивших чем-то кроме мьюта.
- **Связность с известными bad-компонентами:** BFS от помеченных узлов.

**Метрики узла (классика):** degree, clustering coefficient, PageRank в подграфе «подозрительных» рёбер.

### 3.6 Устройство, сеть, скорость регистраций

*(Частично **вне** Telegram, через Mini App / WebApp / ваш API.)*

| Сигнал | Зачем |
|--------|--------|
| **IP** | Кластер «много signer’ов с одного /24» |
| **ASN** | Датацентры, хостинг |
| **Гео (грубо)** | Несоответствие заявленному региону продукта |
| **User-Agent / Client Hints** | Автоматизированные клиенты (осторожно: подделка) |
| **Стабильный device token** (с согласия) | Связка мультиаккаунтов |
| **Velocity** | `accounts_created / IP / hour` |

**VPN/прокси:** коммерческие списки + эвристики latency/TTL (всё с ошибками, только как **слабый** сигнал).

### 3.7 Видео: свежесть, liveness, согласованность

**Свежесть / anti-replay:**

- Метаданные контейнера (`ffprobe`).
- **pHash / dHash** кадра или серии кадров; Hamming distance до БД недавних загрузок.
- **Challenge–response:** случайный жест + фраза + движение головы; хранить `nonce`, TTL, одноразовость.

**Liveness (живость):**

- Моргания, микродвижения лица, `optical flow` фона vs переднего плана.
- Несогласованность освещения лица и фона (грубый deepfake/fake cam).
- Регулярность кадров: **слишком стабильный** FPS без дропа у записи с «мобилки» — иногда признак ретрансляции (не железно).

**Сопоставление лиц:**

- Эмбеддинги (ArcFace и др.) + косинус к аватару / к документу (если есть юридическое основание).

$$
\mathrm{sim}(\mathbf{e}_v, \mathbf{e}_p) = \frac{\mathbf{e}_v \cdot \mathbf{e}_p}{\lVert \mathbf{e}_v \rVert \lVert \mathbf{e}_p \rVert}
$$

**Жесты:**

- MediaPipe Hands; вероятность класса $P(g\mid \mathrm{frame})$; сверка с challenge.

**Склейка в скор (пример уже в документе):**

$$
s_{\mathrm{fresh}} = w_1 \mathbf{1}(\mathrm{challenge\ ok}) + w_2 \bigl(1 - \min(1, d_{\mathrm{pHash}}/d_{\max})\bigr) + w_3 f_{\mathrm{meta,norm}}
$$

$$
s_{\mathrm{live}} = \alpha \,\mathrm{norm}(\sigma^2_{\mathrm{face}}) + \beta \,\mathrm{norm}(N_{\mathrm{blink}}) + \gamma \,\mathrm{norm}(\Delta_{\mathrm{yaw}})
$$

### 3.8 Голос и аудио (если принимаете voice)

- **Качество записи:** SNR, наличие сетевых артефактов.
- **Спикер-эмбеддинг:** сравнение с прошлыми успешными верификациями того же аккаунта.
- **ASR + сверка с challenge-текстом** (например произнести код).

Ограничения: хранение аудио = **ПДн** / согласия.

### 3.10 Honeytokens, канарейки, водяные знаки

- Уникальная **реферальная ссылка** или промокод на пользователя: утечка в спам-кампаниях помогает найти источник.
- **Водяной текст** в challenge («повторите фразу X» с уникальным X) в логах правоохранения и модерации.

Не нарушайте **приватность** и закон о маркетинге без оснований.

---

### 3.11 Rate limiting, квоты, экономика злоупотреблений

- **Token bucket** на `user_id`: сообщения/мин, callback/мин.
- **Глобальные** лимиты на IP / ASN на signup (если контролируете регистрацию).
- **Эскалация:** при приближении к лимиту — CAPTCHA-подобный шаг (в Telegram — видео-challenge).

Цель — поднять **стоимость атаки** линейно или сверхлинейно.

---

### 3.12 Репутация, жалобы, обучение с учителем

**Trust / reports:**

$$
T = T_0 + \kappa_1 \mathbf{1}(\mathrm{verified\ video}) + \kappa_2 A_{\mathrm{account}} - \kappa_3 R_{\mathrm{reports}} - \kappa_4 B_{\mathrm{blocks}}
$$

- Взвешивание репортов по репутации репортёра.
- Защита от **мафии** (сговор репортов): граф репортов, корреляция с новыми аккаунтами.

**Разметка:**

- Собирайте `feature_vector → label` (бот / человек / неясно) для **LightGBM** / **XGBoost**.
- Калибровка вероятностей: **Platt** / **isotonic** для честного $p$.

---

### 3.13 Ансамбль и интерпретируемость

- **Stacking:** логрег поверх вероятностей подмоделей (текст / ритм / видео).
- **SHAP / feature importance** для объяснения аналитикам и Compliance.

---

### 3.14 Адаптивный противник: чего ждать

| Атака | Митигация |
|-------|-----------|
| **LLM переписывает текст** | Поведение + граф + видео-challenge; перплексия не панацея |
| **Ферма людей** | Сложные challenge, временные несовпадения, связка с оплатой |
| **Deepfake видео** | Многофакторный скор, аудио, противоречивые сигналы, обновление детекторов |
| **Replay видео с экрана** | Optical flow, мoiré, reflection detection (продвинуто) |
| **Покупка аккаунтов** | Поведенческий сдвиг + re-verification по триггерам |

Ни один слой не даёт 100%; **defence in depth**.

## 4. Видео-слой (краткая сводка формул)

Метрики **f_meta**, **f_pHash**, **f_challenge** — см. §3.7.

$$
\mathrm{sim}(\mathbf{e}_{\mathrm{video}}, \mathbf{e}_{\mathrm{profile}}) = \frac{\mathbf{e}_v \cdot \mathbf{e}_p}{\lVert \mathbf{e}_v \rVert \, \lVert \mathbf{e}_p \rVert}
$$

Связка жеста с заданием: $P(g \mid \mathrm{frame}) > \tau_g$.

## 5. Поведение в чате с ботом (формулы)

Интервалы $\Delta t_i$:

$$
\lambda = \frac{N_{\mathrm{msg}}}{T_{\mathrm{window}}}, \qquad
\mathrm{CV} = \frac{\mathrm{std}(\Delta t)}{\mathrm{mean}(\Delta t) + \varepsilon}
$$

Энтропия текста:

$$
H = -\sum_{c} p(c)\,\log p(c)
$$

Дубликаты:

$$
r_{\mathrm{dup}} = \frac{\#\text{почти дубликатов}}{\#\text{сообщений}}, \qquad
\mathrm{sim}_{\mathrm{text}}(m_i,m_j) = \cos(\mathbf{v}_i,\mathbf{v}_j)
$$

## 6. Trust / Risk Score

### 6.1 Вектор признаков (пример)

| Признак | Описание |
|---------|----------|
| `messages_per_min` | $\lambda$ |
| `response_time_cv` | $\mathrm{CV}$ |
| `text_entropy` | $H$ |
| `dup_ratio` | $r_{\mathrm{dup}}$ |
| `link_*` | бинарные флаги |
| `face_match_sim` | косинус лиц |
| `liveness_score` | $s_{\mathrm{live}}$ |
| `video_fresh_score` | $s_{\mathrm{fresh}}$ |
| `report_count_weighted` | жалобы с весом репортёра |
| `shadow_hint_count` | мягкие накопленные сигналы |
| `action_sequence_kl` | отклонение от «нормальной» матрицы переходов |
| `coordination_score` | близость к кампании дубликатов |

> **Возраст аккаунта в Telegram:** Bot API **не** возвращает дату регистрации. Замена: свой `first_seen_at`, CRM, платежи, слабые внешние сигналы.

### 6.2 Модель MVP

$$
S = 100 \cdot \sigma\!\left( \beta_0 + \sum_k \beta_k z_k \right), \qquad \sigma(x)=\frac{1}{1+e^{-x}}
$$

Далее: **XGBoost** / **LightGBM**.

### 6.3 Ручная развесовка

$$
R = \min\left(100,\; w_1 S_{\mathrm{spam}} + w_2 S_{\mathrm{behav}} + w_3 S_{\mathrm{video}} + w_4 S_{\mathrm{reports}}\right)
$$

### 6.4 Зоны и действия

| $R$ | Действие |
|-----|----------|
| 0–30 | Доп. проверки, капча, лимиты |
| 30–70 | Норма |
| 70–100 | Повышенный trust |

Семантика $R$ должна быть **зафиксирована** (иногда высокий = опасный — тогда инвертировать таблицу).

**Action layer:** $R > R_{\mathrm{hard}}$; $R_{\mathrm{soft}} < R < R_{\mathrm{hard}}$ → shadow-ban; $R > R_{\mathrm{challenge}}$ → видео-задание.

## 7. Быстрые эвристики

| Флаг | Условие |
|------|---------|
| Ранний линк | ссылка в первых $k$ сообщениях |
| Спам-шаблон | одно сообщение $\ge n$ раз за $T$ |
| Пустые исходы | много стартов без целевого ответа |
| Burst | $\lambda \gg$ медианы за сутки |

## 8. Ошибки, которых избегать

- Один только текст или одна фотография без challenge/liveness.
- Мгновенный бан без скоринга и аудита.
- Игнор поведения и координации.
- Нет жалоб и апелляций.

---

## 9. Приоритет внедрения

1. Ритм + дубликаты + ссылки + лимиты.
2. Видео **challenge** + liveness + pHash.
3. Граф координации (по мере объёма).
4. Модель $R$ + action layer + калибровка.
5. Device/IP слой через Mini App / бэкенд.
6. Спикер/голос при юридической базе.

## 10. Зачем делать именно это: продукт, деньги, риски

**Общая логика:** антифрод — это не «витрина ML», а **снижение ожидаемых потерь** и **стоимости операций**. Каждая мера должна иметь ясный источник выгоды.

| Зачем | Почему имеет смысл |
|-------|---------------------|
| **Risk score + мягкие действия** | Жёсткий бан удорожает **ложные срабатывания** (потеря платящих клиентов, репутация, иски). Градация (лимиты → challenge → бан) **оптимизирует ожидаемую прибыль**. |
| **Поведение (ритм, RT, burst)** | Дёшево в вычислениях, **хорошо ловит скрипты** и массовые сценарии без тяжёлого CV. Снижает нагрузку на людей и на дорогие проверки. |
| **Дубликаты текста / URL** | Скам почти всегда **шаблонный**. Ловля дубликатов даёт **высокий отсев при низкой цене** и хорошие доказательства для модерации. |
| **Лимиты и квоты** | Поднимают **маржинальную стоимость атаки** линейно; часто **сильнее**, чем «умный» ML на слабом потоке. |
| **Video challenge + liveness** | Дороже CPU/GPU, но **главный барьер против replay и простых ферм** там, где только текст уже не спасает. Имеет смысл **не на каждое сообщение**, а по триггеру скора или этапу воронки. |
| **Граф координации** | Полезен при **масштабе** (кампании, накрутки рефералок). Без объёма событий ROI откладывается. |
| **Жалобы + вес репортёра** | Закрывает «дыру», которую не закроет модель: **новые паттерны** и сигнал от доверенных пользователей. Обязателен для продакшена с UGC. |
| **Device / IP при Mini App** | Сильный сигнал для **Sybil** и массовых регистраций; требует юридической базы под данные. |

**Итог:** сначала максимизируйте **дешёвые сигналы с высоким precision на «очевидную грязь»**, затем включайте тяжёлые модели **условно** (по скору), иначе сожжёте маржу на инфраструктуре.

## 11. Нагрузка на сервер: ориентировочные оценки

Цифры **порядка величины** для планирования (зависят от языка, железа, батчинга, квантизации). Не заменяют профилирование на вашем стенде.

### 11.1 В пути «ответ пользователю» (синхронный критичный путь)

Задача: не убить UX бота (пользователь ждёт ответ; Telegram сам по себе не любит долгие хвосты).

| Метод | CPU | RAM на запрос | Порядок задержки | Комментарий |
|--------|-----|----------------|------------------|-------------|
| Правила + лимиты (Redis) | низк. | < 5 МБ | **< 1–3 ms** | Делать **всегда** первым слоем. |
| $\Delta t$, CV, простые счётчики | низк. | десятки КБ | **< 1–5 ms** | Чистая математика по кэшу. |
| Энтропия / Jaccard / n-gram по одному сообщению | низк. | сотни КБ | **~ 1–20 ms** | Зависит от длины текста. |
| TF-IDF / BM25 к небольшому индексу | ср. | десятки МБ (индекс) | **~ 5–50 ms** | Кэшируйте индекс шаблонов в памяти. |
| Sentence embedding **CPU**, 1 строка | ср.–выс. | сотни МБ–1 ГБ (модель) | **~ 30–200 ms** | Батч по очереди сильно дешевле per-unit. |
| Sentence embedding **GPU** | ср. | VRAM 2–8 ГБ | **~ 5–30 ms** / батч | Имеет смысл при высокой **секундной** нагрузке. |
| **Один** perceptual hash + поиск по 10⁶ хэшей | низк.–ср. | зависит от БД | **~ 5–30 ms** | Hamming по Битмапу / Redis / ключу. |
| MediaPipe Hands + Face, **мало кадров** (напр. 8–12) на **CPU** | высок. | 200–800 МБ процесс | **~ 0.2–2 s** | Не класть в горячий путь каждого сообщения. |
| Тяжёлый face embedding (ArcFace) + GPU | высок. | VRAM | **~ 10–80 ms** / изображение | Батч и отложенная очередь. |
| «Толстая» нейросеть liveness (коммерч. уровень) | очень высок. | GPU | **сотни ms – сек** | Только выборочно или отдельный воркер. |

**Практика:** в HTTP/webhook-обработчике бота держите **< 50–100 ms** суммарно на «лёгкие» фичи; всё, что > 200–300 ms по медиане, выносите в **очередь** (Celery / RQ / SQS) и шлёте пользователю «проверяем, пришлём результат» или ставьте **только на шаге онбординга**, а не на каждый диалог.

### 11.2 Фон / батчи (асинхрон)

| Задача | Нагрузка | Когда считать |
|--------|----------|----------------|
| MinHash LSH, дедуп по миллионам сообщений | CPU + память + диск | Периодически (cron) |
| Пересчёт графовых метрик | высок. RAM | Раз в час/сутки |
| Обучение LightGBM | CPU, пики | Редко; отдельный инстанс |
| Логи + OLAP (ClickHouse и т.д.) | диск, IO | Постоянно, но не в hot path |

### 11.3 Хранилище и сеть

- **Видео/кружки:** хранение сырья дорого и чувствительно к ПДн; чаще храните **хэши, эмбеддинги, метаданные**, сам файл — TTL 24–72 ч или только в SpO режиме.
- **Исходящий трафик:** скачивание файлов с Telegram + обработка — учитывайте в **bandwidth** воркеров.

### 11.4 Орден величины «инстанс нагрузки» (иллюстрация)

Условно: **1 vCPU**, лёгкий контур без тяжёлого видео на **каждое** сообщение — **сотни–пары тысяч простых** запросов/с (если только логика+Redis).  
Тот же контур, если на **каждый** апдейт гнать **полный CV-трубопровод** — упираетесь в **десятки** одновременных пользователей на ядро.

**Вывод инженерный:** **кондициональная** тяжёлая обработка (топ 5–20% «подозрительных» по дешёвым фичам) часто даёт **90% эффекта при 20% CPU**.

## 12. Максимальный профит (ROI): что внедрять и в каком порядке

**Профит** в широком смысле:

$$
\Pi \approx \underbrace{L_{\mathrm{fraud}}}_{\text{предотвращённые потери}} + \underbrace{C_{\mathrm{mod}}}_{\text{сэкономленные часы модерации}} + \underbrace{R_{\mathrm{conv}}}_{\text{рост конверсии «живых»}} - \underbrace{I_{\mathrm{infra}} + I_{\mathrm{dev}}}_{\text{инфра + разработка}}
$$

Точные $L_{\mathrm{fraud}}$ нужно оценивать по вашим chargeback/stolen promo/abuse метрикам.

### 12.1 Матрица «эффект / стоимость» (качественно)

| Мера | Эффект на фрод | Стоимость внедр. | Стоимость эксплуатации |
|------|----------------|------------------|-------------------------|
| Лимиты, burst, ранние линки | **высок.** на массовых ботах | низк. | почти ноль |
| Ритм ($\lambda$, CV, RT) | **высок.** на скриптах | низк. | низк. |
| Дубликаты / шинглы | **очень высок.** на скам-шаблонах | низк.–ср. | ср. (память индекса) |
| Простой risk score (логрег) | ср.–выс. | низк. | низк. |
| Challenge **без** тяжёлого liveness | **выс.** против replay | ср. | ср. (хранение, CV CPU) |
| Полный liveness + face embedding | **выс.** против ферм/дорогих атак | высок. | **очень высок.** |
| Граф координации | **выс.** при больших кампаниях | высок. | высок. (данные) |
| Жалобы с весами | **выс.** на новых паттернах | ср. | ср. |

### 12.2 Парето-фронт (рекомендуемая последовательность под максимум $\Pi$)

1. **Лимиты + эвристики ссылок + дубликаты** — чаще всего **лучший $\Pi$/день** на старте: почти не жрут CPU, отсекают мусор массово.  
2. **Поведенческий слой ($\Delta t$, CV, burst, последовательности)** — дешёвое усиление против автоматизации.  
3. **Условное видео-challenge** только для пользователей с $R > R_*$ или на **ключевом шаге** (вывод, бонус, рефералка) — резко снижает **$I_{\mathrm{infra}}$** при сохранении защиты там, где больно.  
4. **Тяжёлый liveness / нейросети** — только когда есть **измеримый** $L_{\mathrm{fraud}}$ без них (пилот A/B).  
5. **Граф + device** — когда выросли объёмы и появились **координированные** атаки; иначе преждевременный **overengineering**.

### 12.3 Что обычно **не** приносит максимум профита в первый месяц

- Тяжёлый CV **на каждое** входящее сообщение без фильтра.  
- Очень сложная graph-neural-network без данных и без команды аналитики.  
- Покупка внешних платных API **до** исчерпания дешёвых внутренних сигналов (если политика компании допускает только внутреннее — тем более).
